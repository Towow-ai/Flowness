# Flowness Launch Runbook

This runbook separates identity correction from category launch so attention is not spent on a claim the public artifact cannot yet demonstrate.

## T-21 to T-14 — freeze the release contract

- select the source commit and release tag;
- freeze the Claim / Evidence Register;
- run every current README command from a clean environment;
- complete English/Chinese semantic parity review;
- decide whether the launch is current-safe or post-Hero-Demo;
- create the immutable evidence manifest.

**Go/no-go:** no public statement has a stronger status than its evidence.

## T-14 to T-7 — prepare the proof surface

- capture deterministic demo video and terminal transcript;
- publish the inspector output and manifest hashes;
- review architecture diagrams against the release;
- seed three Failure Atlas cases;
- prepare maintainers for issue triage and reproducibility support;
- send an embargoed one-pager to a small group of technical reviewers.

**Go/no-go:** a stranger can run the proof without private credentials.

## T-7 to T-1 — prepare distribution

- update GitHub About, social preview, README, docs index, and release notes in one branch;
- schedule Chinese long-form and English short-form posts;
- prepare Product Hunt only for the post-Hero-Demo release;
- prepare Show HN only when the public proof is immediately runnable;
- verify links, mobile layout, alt text, and screenshots;
- assign launch-day roles: release owner, technical responder, community responder, incident owner.

## T0 — release sequence

1. publish the tagged GitHub release and evidence manifest;
2. verify the release from a fresh clone;
3. merge the public README/site branch;
4. publish the long-form category explanation;
5. publish platform-specific posts pointing to the same release;
6. open one pinned discussion: “What should Flow Engineering measure?”;
7. log every launch claim and external correction.

## T+1 to T+7 — convert attention into evidence

- prioritize reproducibility failures over feature requests;
- publish corrections quickly and visibly;
- invite mechanism-level contributions, not only full-framework adoption;
- hold the first Flow Clinic around one real failure;
- record questions that indicate positioning confusion;
- update FAQ and diagrams rather than repeatedly explaining in comments.

## T+8 to T+30 — compound the category

- release one Failure Clinic fixture;
- publish one mechanism deep dive;
- recruit at least one independent FlowBench provider;
- create an RFC from repeated community disagreement;
- report launch outcomes using reproductions, borrowed mechanisms, and evidence-bearing contributions—not impression volume alone.
