# Flowness Open-Source Launch Strategy

The launch should establish a category, show a runnable proof, and invite technically meaningful participation. It should not look like a one-day marketing spike around an oversized “autonomous coding” claim.

## 1. Launch objective

The primary objective is **category ownership through credible articulation and evidence**:

> Flow Engineering is the engineering of work in motion. Flowness is a work-centered runtime for agentic software engineering.

Secondary objectives:

- show that Towow has accumulated first-hand Harness experience;
- attract builders who have felt long-horizon agent failures;
- turn private dogfood learning into public Failure Atlas assets;
- find contributors for WorkView, hero demo, FlowBench, and failure fixtures;
- establish Nature / Towow Research as a serious independent voice in agent engineering;
- create reusable mechanisms even for teams that do not adopt the full runtime.

Do not optimize the launch around short-lived stars alone.

## 2. Readiness levels

### Launch A — Identity and Assurance Kernel

Can launch after:

- current-safe README is merged;
- architecture and concept docs are live;
- Assurance Kernel demo passes from clean clone;
- claim register and community files are present;
- all public release files are hash-bound.

Message:

> We are publishing a work-centered runtime direction, a runnable assurance kernel, a substantial inspectable mechanism set, and an empirical Failure Atlas program.

Do not submit this version as a Show HN unless visitors can run something immediately. The Assurance Kernel satisfies the “play with it” threshold, but the title must be narrow and honest.

### Launch B — Work Outlives Agents

Preferred category launch after:

- WorkView CLI is public;
- hero demo passes;
- `agents:none / flow:alive` is real;
- graph v1 → v2 occurs from a Finding;
- release/evidence binding is complete.

Message:

> Work survives agents and recompiles its next execution from the current world.

This is the best moment for Product Hunt, Show HN, the main English launch article, and a launch video.

### Launch C — Public organic E2E / FlowBench

Research and credibility launch after:

- a new public task traverses the full SWE profile;
- an independent provider or reviewer reproduces it;
- FlowBench qualification passes.

Message:

> Here is a falsifiable comparison and complete replay, not only a framework story.

## 3. Narrative sequence

Every launch surface should use this order:

1. **Felt problem:** Agents finish; Work does not necessarily finish.
2. **Industry map:** Prompt → Context → Harness → Loop → Graph → Flow.
3. **New subject:** Work persists; Agents assemble.
4. **Human control:** Humans govern the constitution, not every transcript.
5. **Mechanism glimpse:** persistent truth, current-world compilation, runtime assembly, reflow, reality closure.
6. **Runnable proof:** what people can run now.
7. **Evidence boundary:** what is inspectable, dogfood, designed, or open.
8. **Invitation:** Learn, Borrow, Build, or challenge.

Avoid opening with 41 mechanisms, D0–D9, formal distributed-systems language, or internal audit counts.

## 4. Audience routes

### Curious builder

Landing route:

```text
README hero → 90-second demo → From Harness to Flow → quickstart
```

Desired action: run demo or star/bookmark.

### Experienced agent engineer

```text
Failure Atlas → architecture → module contracts → Flow Clinic
```

Desired action: submit counterexample, fixture, or mechanism comparison.

### Open-source contributor

```text
CONTRIBUTING → good first fixtures → WorkView task → Discussions
```

Desired action: reproduce a case or improve a public contract.

### Researcher

```text
whitepaper / technical report → claim register → FlowBench → formal artifacts
```

Desired action: critique assumptions, implement a baseline, or reproduce a theorem/fixture.

### Owner / enterprise reader

```text
Human Constitution → Cognitive Exoskeleton → organic E2E case → governance docs
```

Desired action: discuss a bounded pilot, not buy a universal automation promise.

## 5. Channel sequencing

### Week -3 to -2: seed the language

Publish short ideas without announcing the full repository:

- “Agent does not own the work. Work temporarily calls an Agent.”
- “A Graph is one version of the road; Flow is the work that keeps traveling when the road changes.”
- “Human out of the session, never out of the constitution.”
- one Failure Atlas case.

Goal: let the audience encounter the vocabulary before launch day.

### Week -1: technical preview

- invite 8–15 respected builders to review README and demo;
- ask each reviewer one explicit question;
- collect objections and update claims;
- do not ask for launch-day upvotes.

### Launch day

Publish in a staggered order:

1. GitHub Release and repository update;
2. project website;
3. English technical post / X thread;
4. Chinese WeChat longform;
5. Zhihu and Juejin adaptations;
6. HN or Product Hunt only when the correct readiness level is met;
7. community posts later in the day with channel-native wording.

### Week +1 to +4

- one mechanism deep dive per week;
- one Failure Atlas case per week;
- one live Flow Clinic;
- publish external feedback, including criticism;
- convert questions into FAQ and fixtures.

## 6. Launch assets checklist

### Required

- bilingual README;
- runnable demo and inspector;
- 90-second video or terminal recording;
- 5-second and 30-second architecture visuals;
- status/claim table;
- Failure Atlas landing page;
- CONTRIBUTING, CODE_OF_CONDUCT, SECURITY, SUPPORT, CITATION;
- one English and one Chinese long-form article;
- platform-native copy;
- release manifest and SHA-256 sums.

### Preferred

- WorkView CLI;
- hero demo;
- static website;
- 12-slide launch deck;
- mechanism cards;
- interactive architecture / trace viewer;
- first three public failure fixtures;
- office-hours calendar.

## 7. Metrics that matter

### Attention

- qualified repository visitors;
- README → quickstart conversion;
- demo completions;
- saves/bookmarks, not only likes;
- external mentions that repeat the intended definition correctly.

### Understanding

Sample new readers:

- Can they explain Flowness in 30 seconds?
- Can they distinguish Work, Execution, Graph, and Flow?
- Can they state what the public demo does not prove?
- Can they explain where humans remain authoritative?

### Community

- external failure fixtures;
- counterexamples;
- Discussions with technical depth;
- independent reproductions;
- recurring contributors;
- translation maintainers;
- benchmark providers.

### Product/research

- time to first public WorkView;
- number of replayable Failure Atlas cases;
- public E2E completion;
- FlowBench qualification;
- mechanisms replaced by simpler mature components;
- repeat-failure reduction.

## 8. Anti-patterns

Do not:

- announce “the first Flow Engineering runtime”;
- claim full autonomy or universal domain support;
- ask communities to star before trying the demo;
- post identical marketing copy everywhere;
- hide current limitations at the bottom;
- lead with formal proofs to a general developer audience;
- turn dogfood failures into self-deprecation;
- use a polished UI to imply unimplemented behavior;
- count model-generated comments as community traction;
- release a benchmark after looking at holdout labels.

## 9. Recommended release title

Current-safe:

> **Flowness Open Alpha — A work-centered runtime direction with a reproducible assurance kernel**

After hero demo:

> **Flowness Open Alpha — Work survives agents and recompiles its next execution**

## 10. One-line invitation

> **Learn from the failures. Borrow a mechanism. Build your own work-centered Harness.**
