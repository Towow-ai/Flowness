# 前向派发 / Forward Handoff

派发是最常见的一种交接：一个编排中的心智，把一件具体的活，交给一个**全新开的、零上下文的 worker**（fix / review / plan / execute / consensus 都属此类）。下面先把这种读者最容易绊倒的两处说清，再用 fix 走一遍改前 / 改后。

## 这个读者：零上下文的新人，两处最容易绊倒它

新 worker 是 SKILL.md 里那种存在的最极端形态——它一生只活在你这封信里，连"以后慢慢熟"都没有。所以有两处倾向，在它身上比平时更要命，信要专门对着使劲：

**它解不了的暗号，它不会问，会脑补。** 一个全新会话查不动 `T-SL`、`FB-3`、`B4-07` 这种系统内部编号——但它不会停下来问"这是啥"。它没有"我不知道"那个信号，会自信地编一个意思接着走，于是从一个错的指称开始，把整条路走歪。所以这种信里，每一个不是常识的术语，要么就地用一句话落地，要么删掉——别留着赌它能查到。

**步骤铺得越满，它越把自己降格成执行器。** 你把"先做这、再做那"写到底，它就照本抄、不敢动用自己的判断——而它的判断往往比那张步骤表更好。所以这种信交的是目标和判断，具体怎么走留给它：你越信它能找路，到场的越是那个会找路的它。

## 五类派发的共性与差异

共性（都走主体那套魂）：一句话目标 → 一两句承重判断（钩它已有的判断，不重教手册）→ 背景指针 → 短的必守打卡 → 冷读自检。

差异只在"承重判断"那一两句钩的是什么、以及打卡点：

- **fix**：钩"干净的闭合长什么样"——修一个问题不制造下一个。打卡：提交修复、收尾、转质检。
- **review**：钩"什么算放行 / 什么必须打回"的判准。打卡：给出结论 + 依据。
- **plan**：钩"好计划的形状"——可执行、有依赖、失败可见。打卡：产出可被下一个 agent 直接接手的计划物。
- **execute**：钩"做到什么算这步成了"。打卡：留下可验证的完成信号。
- **consensus**：钩"什么时候算对齐了"。打卡：记下分歧点与裁决依据。

写新的一类时，不要重写这套结构——它是同一个魂，只换"钩哪一句判断"。

## fix 范例 · 改前

下面这封是真实在用的 fix 派发信（节选自一次诊断）。它读起来像"一个半夜很焦虑的技术负责人给实习生写的交接"——病灶逐条标在后面。

> 你被 F-11 orchestrator daemon 自动 dispatch 到 fix skill (M-1.6)。装人格 (load `.claude/skills/fix/SKILL.md`) 后处理以下 trigger。
> 本次 trigger 因 FB-3 并发帽耗尽被延后派发。
> 待修：T-SL 关联的 B4-07。**不带 `--session-id` 会被拒**；**漏带 trigger 引用会被拦**；**改动越界会砸掉 review agent 的账本 (DOGFOOD-001-U)**。
> 你必须：严格遵守 `fix/SKILL.md` 全部 8 条；不得重写；不得顺手优化；先读 knowledge (≈83KB) 再动手……

病灶：
- **目标缺席**。通篇没有一句"这次要把什么修成什么样"。第一句是身份和管线编号。
- **内部账漏成指令**。"因 FB-3 并发帽耗尽被延后派发"是调度器记给自己看的账，对干活的人零用处，还留下一个解不了的 `FB-3`。
- **一堆解不了的暗号**。`F-11`、`M-1.6`、`T-SL`、`B4-07`、`DOGFOOD-001-U`——全新会话一个都查不动，它会脑补。
- **喂恐惧**。"会被拒 / 会被拦 / 会砸掉别人账本"——还没说清要干嘛，先把求稳的水位拉满。
- **人格 cosplay + 手册重抄**。"装人格"误导它去"演个身份"；"严守 8 条"把工作手册已讲透的东西又抄了一遍。
- **把沼泽推给它**。"先读 ≈83KB knowledge 再动手"=让它自己去翻一片没分层的资料。

## fix 范例 · 改后（已接真源头，真实渲染形态）

下面是真实生成器（`l2/dispatch_templates.py`）现在渲染出的 fix 派发信（约 460 字）：

> /fix
>
> **问题**: 〔finding 现象，生成器从真实 trigger 填〕
> **严重度**: 〔sev〕 · **记录 id (finding_id)**: 〔id〕
>
> **现场信息（开工要用的）**:
> - 你的真判据 = 这条 finding 的闭合合约（怎样算闭合、要同步哪些连带处、哪些残留清零）：跑 `grep '<event_id>' <账本>` 把完整 payload 调出来、照合约修
> - 这批代码基线 commit: 〔hash〕（落后就先 rebase 再开工）
> - 所有 towow 命令带 `--project-dir=<主仓>/harness`

变化：短了一半多（旧模板 3500+ → 460）；人格不再"叫它去读手册"，改成**第一行 `/fix` slash 直接把 fix skill 装上**——目标、"修一个不制造下一个"、干净闭合的判断都在 skill 里，信不重抄；"装人格"和所有解不了的编号没了；恐惧句翻成正向；打卡压短。

**这里藏着前向派发最容易漏的一层——认知闭环在上游、信的活是指向它。** fix 这次的"肉"不是信能现编的：怎样算修干净，是 review 写在**闭合合约**里的。所以信的本职不是把"去拿合约"写成机械的一步，而是**点名"你的真判据 = 这条 finding 的闭合合约"**，把读者明确推向那份上游真简报。同理：execution 的真简报是 task 包（含 `done_criteria`——success 门照它复算）、planning 的是冻结的共识、consensus 的是 brief。**前向派发的认知闭环几乎都在上游产物里——派发信真正不可替代的活，就是把读者明确指向那份真简报，而不是把"去拿它"写成机械步骤。**（这条是 fix/execution 实迁后回灌的教训：第一版只做到删代号+写短，漏了"指向真简报"这层肉。）
